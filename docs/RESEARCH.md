**確認できた事実**と**私の設計判断(暫定)**を区別して書く。

## A. 睡眠スコア

### A-1. 確認できた事実
**業界標準のスコア式は存在しない。** Oura、Fitbit などは配点を非公開にしている。公開情報から分かる範囲は次のとおり。

- Oura は、総睡眠時間、睡眠効率、Restfulness、REM、Deep、入眠潜時、就寝時刻の一貫性の加重合成。配点と閾値は非公開([Oura Member Care](https://support.ouraring.com/hc/en-us/articles/360025445574-Sleep-Score))。
- Fitbit は、Duration(最大50点)、Deep & REM(最大25点)、Restoration(最大25点)に分かれる。ただし配点は二次資料による(出典: [Kygo Health](https://www.kygo.app/post/every-sleep-metric-your-wearable-tracks-oura-apple-watch-fitbit-garmin))。
- 多くのスコアは、Duration / 睡眠の質 / タイミングの規則性、の3系統の組み合わせ。**SPEC の4要素(Duration / Restoration / Consistency / Feeling)もこの構造の範囲内**。

**学術的に確認できた基準値(これをスコアの根拠にする)**

| 指標 | 基準 | 出典 |
|---|---|---|
| 睡眠時間(成人) | AASM/SRS: 7時間以上。NSF: 7〜9時間(65歳以上は7〜8時間) | [AASM 発表](https://aasm.org/aasm-and-srs-publish-new-sleep-duration-consensus-statement/)、[NSF Hirshkowitz 2015](https://www.sleephealthjournal.org/article/S2352-7218(15)00160-6/abstract) |
| 入眠潜時 | 30分以内が適切(全年齢共通)。成人は31〜45分が「不確か」、46分以上が「不適切」 | NSF 睡眠の質 consensus([Ohayon 2017](https://escholarship.org/uc/item/9xc5x5h2))の Fig. 2 |
| 5分を超える覚醒の回数 | 成人は0〜1回が適切、2〜3回が不確か、4回以上が不適切 | 同 Fig. 3 |
| 入眠後の覚醒時間(WASO) | 20分以下が適切。成人は51分以上が不適切 | 同 本文 |
| 睡眠効率 | 85%以上が適切。74%以下が不適切(若年成人は64%以下) | 同 本文 |
| REM / 深い睡眠の割合 | 成人の REM は21〜30%、N3(深睡眠)は16〜20%が適切。ただし**ステージ指標は、連続性の指標より合意が弱い** | 同 本文(要旨にも「睡眠構造は合意が少ない」とある) |
| 規則性 | Sleep Regularity Index(SRI): 24時間離れた2時点で同じ状態(睡眠/覚醒)である確率。死亡リスクの予測では、睡眠時間より強い関連が報告されている | [Phillips 2017 系の解説](https://wadpac.github.io/GGIR/articles/SleepRegularityIndex.html)、[Sci Rep 2018](https://www.nature.com/articles/s41598-018-32402-5) |

### A-2. 設計の考え方(私の判断)
- **Restoration は、ステージ(Deep/REM)ではなく「睡眠の連続性」で評価する。** マイクだけではステージを正確に推定できない(PLAN §2)上に、NSF の合意も、連続性の指標(潜時・覚醒・WASO・効率)のほうが強い。SPEC の「Restoration」の名前は変えず、中身を連続性指標にする。
- 閾値は、NSF の「適切」「不適切」の境界に合わせて、その間を線形補間する。
- **要素間の配点や各段階のスコア化は標準がなく、設計判断になる。** 実データで調整する前提で、定数を `Thresholds.kt` に集約する。

### A-3. 暫定式(承認してほしい)
合計 100 点。

| 要素 | 配点 | 算出 |
|---|---|---|
| Duration | 40 | 総睡眠時間 TST で決める(下記) |
| Restoration | 30 | 4つの連続性指標の重み付き平均(下記) |
| Consistency | 20 | 直近7夜の就寝時刻・起床時刻のばらつき(下記) |
| Feeling | 10 | 起床時の気分 1〜5 を 0〜100% に換算(`(気分-1)/4`) |

**Duration**(目標睡眠時間 G は設定値。既定は 7.5 時間)
- TST が 4 時間以下は 0%。4 時間から G まで線形に増加し、G 以上 9 時間以下で 100%。
- 9 時間を超えると緩やかに減点(1時間あたり 10%、下限 70%)。AASM は上限を置いていないため、減点は弱くしている。
- 4時間未満はスコアなし(SPEC の FR-2.7)。

**Restoration**(各指標を 0〜100% にして重み付き平均)
| 指標 | 100% | 0% | 重み |
|---|---|---|---|
| 睡眠効率 | 85% 以上 | 74% 以下 | 0.4 |
| WASO | 20 分以下 | 51 分以上 | 0.2 |
| 5分超の覚醒回数 | 0〜1 回 | 4 回以上(2〜3 回は 50%) | 0.2 |
| 入眠潜時 | 30 分以下 | 46 分以上 | 0.2 |
- 各「100% と 0% の間」は線形補間する。

**Consistency**
- 就寝時刻と起床時刻それぞれの、直近7夜の標準偏差(SD)から算出する。SD 30 分以下で 100%、90 分以上で 0%、間は線形補間。2つの平均をとる。
- 3夜未満は「データ不足」として、この要素を除いて配点を再配分する。
- 本来の SRI は、24時間の睡眠/覚醒を連続して追う指標。夜間セッションのデータしかないので、簡易版で始める。**この SD の閾値(30/90分)は根拠が弱い設計値。**

**Feeling が未入力の場合**は、この要素を除いて、残りで再配分する。

**区分**(暫定)
| スコア | 区分 |
|---|---|
| 85 以上 | Excellent |
| 70〜84 | Pretty Good |
| 55〜69 | Fair |
| 55 未満 | Poor |

**スコアを出さない条件**: TST が 4 時間未満、Short Sleep、またはセッションが「中断」。理由は FR-4.4 のページに表示する。

## B. 音分類モデル(YAMNet)

### B-1. 確認できた事実
- **YAMNet**は、AudioSet の 521 クラスを予測する事前学習済みモデル。MobileNet v1 アーキテクチャ。入力は 16kHz モノラル、1回の解析窓は約 0.96 秒。README には約 370 万の重みとある([公式 README](https://github.com/tensorflow/models/tree/master/research/audioset/yamnet))。**現在の録音形式(16kHz/モノラル)とそのまま合う。**
- Android 向けには、量子化済み TFLite 版がある(固定長 15600 サンプルの入力)([TensorFlow Lite の説明](https://tensorflow.google.cn/lite/examples/audio_classification/overview))。
- **クラス一覧(公式の `yamnet_class_map.csv` を確認済み)**: 睡眠に関係するものは次のとおり。

| 睡眠アプリの区分 | YAMNet のクラス |
|---|---|
| いびき | Snoring (38) |
| 寝言 | Speech (0)、Whispering (12) |
| 咳 | Cough (42)、Throat clearing (43) |
| おなら | Fart (55) |
| 足音 | Walk, footsteps (48) |
| 動物 | Dog (69)、Bark (70)、Cat (76)、Meow (78) など |
| 呼吸関連(無呼吸の補助) | Breathing (36)、Gasp (39)、Snort (41)、Wheeze (37) |
| その他 | Sneeze (44)、Sniff (45)、Burping (53) など |

- **歯ぎしりに対応するクラスはない**(Chewing (49) が近いが別物)。
- **寝言は Speech と区別できない。** テレビ、同居人の声も Speech になる。
- ライセンス: 公式リポジトリの LICENSE で、`/research` 配下は **Apache 2.0** と確認した。重みについては、作者の Dan Ellis が公式のメーリングリスト([audioset-users](https://groups.google.com/g/audioset-users/c/Ly4guQnlv_o))で「YAMNet は Apache License 2.0 で配布されている」と回答している(2026-09-19 確認)。**ただし、Kaggle のモデルページ(現在の配布元)のライセンス欄は、取得できず未確認。** 個人利用なら、この根拠で進めて実害はないと判断する。ストア公開など再配布をする段階では、Kaggle のページで再確認する。学習に使われたデータ(AudioSet)側の条件は、今回は調べていない。

### B-2. 精度についての証拠
- スマホでのいびき検出の研究はある。例: 6万件以上で学習した独自の DNN で、感度 86.3%、特異度 99.5%(スピーカーでの再生+iPhone 13、18人分の音源)([JMIR / PMC](https://pmc.ncbi.nlm.nih.gov/articles/PMC11970566/))。別の研究では、CNN で感度 89.7%、特異度 88.5%([Nat Sci Sleep 2025](https://www.tandfonline.com/doi/full/10.2147/NSS.S514631))。
- ただし、**これらは YAMNet の評価ではない**。YAMNet でいびきを検出したときの、寝室での実測精度を示す資料は見つけられなかった。
- 研究側も、少人数であること、スマホの置き場所や環境のばらつきを限界として挙げている。

### B-3. 結論(私の判断)
- YAMNet を**「Phase 3 で検出したイベントのクリップ」だけに適用する**。一晩中回し続けると電池を食うため。
- 採用は、**実データで検証してから**決める。決定事項 #1(開発中だけ全録音を残す)を使い、自分の数夜分を録音して正解ラベルを付け、いびき・咳の precision / recall を測る。基準に届かなければ、音量・周期性のルールベースを併用するか、置き換える。
- 歯ぎしりは、モデルでは分類せず「その他」にまとめる(FR-4.7 は部分対応と明記)。
- 無呼吸は、YAMNet にクラスがないので、**ルールベース(いびきの後の無音区間、その直後の Gasp/Snort)**で目安を出す。
- 導入前に確認すること: 重みのライセンス、TFLite の実行方法(LiteRT を直接使う想定。Task Library を使う場合は現在の保守状況を確認する)。

### B-4. 導入方法の調査(2026-09-19 追記)
- **Task Library(`tensorflow-lite-task-audio`)は使わない。** Maven で確認した最新は 0.4.4 で、最終更新は **2023-07-12**。3年以上更新がなく、AGP 9 / targetSdk 37 との相性も未確認。
- **LiteRT(`com.google.ai.edge.litert`)を直接使う。** 公式ドキュメントで、最新は **2.2.0(2026-08-14)**。ただし、ドキュメントで確認できたのは新しい CompiledModel API の説明までで、**YAMNet の TFLite を従来の Interpreter 相当の API で動かせるかは未確認**。着手時に、最小のスパイクで確かめる。
- 入力は、固定長 15,600 サンプル(約 0.975 秒、16kHz/モノラル、-1〜1 の float)。出力は 521 クラスのスコア。Phase 3 のクリップ(16kHz/モノラル/16bit WAV)をそのまま渡せる。前処理(メルスペクトログラム)はモデル内に含まれる版を使う。
- クリップは最大 60 秒 + 前後の余白。0.975 秒の窓を 0.5 秒刻みでずらして推論し、クラスごとの最大スコアで、イベントの種別を決める想定。
- **未確認のこと(実装前のスパイクで確かめる)**: LiteRT 2.2.0 での YAMNet の実行方法、モデルファイルの入手先とサイズ(アプリの assets に同梱)、端末での推論時間。
- **スパイクで分かったこと(2026-09-19)**: ① LiteRT 2.2.0 は Google Maven にあり、従来の `org.tensorflow.lite.Interpreter` を含む。② `litert` と `litert-api` の名前空間が重複していて AGP 9 でマニフェストのマージが失敗するため、`gradle.properties` に `android.uniquePackageNames=false` を追加して回避した(ライブラリ側の作りの問題。将来のバージョンで直れば外せる)。③ モデル(4.1MB、SHA-256 `10c95ea3…`)は、Kaggle 経由と公式サンプルの配布元で同一。ファイル内のメタデータに「Apache License. Version 2.0」の記載と、521 クラスのラベルが入っている。④ ラベルの並びは調査済みのクラス番号と一致(0 Speech、36 Breathing、38 Snoring、42 Cough)。
- **スパイクの実機結果(2026-09-19、OPPO / ColorOS 14)**: 推論は 1 窓あたり約 3〜5 ms(5 秒のクリップ 11 窓で 34 ms、8 秒 17 窓で 54 ms)。一晩 20 クリップでも、合計で数秒以内。電池・時間の面で問題にならない。話し声のクリップは Speech 0.96〜1.00、拍手のクリップは Hands 0.67 / Cap gun 0.80 で、妥当な結果。いびきは未テスト(Snoring は 0.01〜0.04 で誤検出なし)。
- **設計への示唆**: クリップには前後の無音を含むため、`Silence`(0.67 など)が常に上位に出る。種別の判定では、Silence を除外し、睡眠に関係するクラスのスコアだけを見る必要がある。
- **無呼吸の目安の設計(2026-09-19)**: 「いびき → 10〜90 秒の無音 → 呼吸音(Snoring / Snort / Gasp / Breathing / Wheeze のいずれかが 0.3 以上)で再開」を候補とする。間に別のイベントが入ると候補にしない。無音は、音が出ていた区間の終わりから次の始まりまで(前後の余白を除く)で測る。重症度は、1 時間あたりの候補数を、AHI の分類の境界(5 / 15 / 30)を借りて分ける。**AHI そのものではない**ため、名称は「目安」とし、1 時間未満の計測では重症度を出さない。既知の限界: いびきの合間の自然な間や、寝返りでも候補になりうる。実データ(数夜分)で、誤検出の多さを見て、閾値(10 秒 / 90 秒 / 0.3)を調整する。
