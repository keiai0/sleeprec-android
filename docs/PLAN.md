## 2. 先に共有しておくリスク
1. **睡眠ステージ(FR-4.1)**: 音だけで Deep/REM を正確に判定するのは難しいです。マイクだけの推定は、実際には「覚醒/睡眠」と、体動・音の多さからの Light/Deep の大まかな推定になります。加速度センサーを併用する案は Phase 5 で決めます。
2. **dB(FR-4.5)**: 端末ごとにマイク感度が違うため、絶対的な音圧(SPL)ではなく、dBFS 基準の**相対値**になります。
3. **無呼吸(FR-4.6)**: 医療機器ではありません。「いびきの後に長い無音区間が続く」というヒューリスティックによる**目安**で、画面にもその旨を表示します。
4. **未確定事項(SPEC §4)**: スコアの計算式、いびき/無呼吸の閾値、スマートアラームの条件は未定です。実データで調整する前提の暫定値で始め、定数を1か所にまとめます。
5. **ストレージ権限(FR-1.3)**: アプリ専用領域は権限不要なので、ストレージ権限は取りません(録音のエクスポートを作る段階で再検討します)。

## 3. 技術方針
- 引き続き DI・アーキテクチャの作り込みはしません。
- 追加する依存: **Room**(セッション・イベントの保存)、**Navigation Compose**(画面遷移)。グラフ描画は Compose の Canvas で自前実装します。
- **解析ロジックは、Android に依存しない純粋な Kotlin 関数**(PCM の配列を受け取って結果を返す)として書きます。JVM のユニットテストと、既存の WAV ファイルを流し込む確認ができ、一晩待たずに検証できます。
- 解析の閾値などの定数は `Thresholds.kt` に集約します。

### Phase 1: 計測セッションと中断検知
**状態**: 完了(2026-09-19)。ビルド・ユニットテスト・実機確認(保存の区分、中断検知)まで済み。
**目的**: 「1回の計測」を保存できる単位にし、途中で止まったことを検知できるようにする。
**FR**: FR-2.7, 2.8, 2.9, NFR-1(一部)

- Room を導入。`Session`(id, 開始/終了時刻, 状態, 終了理由, WAV パス)。
- 終了時の分岐: 10分未満は保存しない / 10〜30分は Short Sleep / 30分以上は通常。
- 終了時ダイアログ(Discard / Short Sleep として保存 / 計測継続)。
- 中断検知: サービスが数十秒ごとに「最終生存時刻」を保存する。次回起動時に、状態が「計測中」のままで生存時刻が古いセッションを「中断」と判定し、ダイアログで案内する(データが不正確な旨も表示)。
- 原因の推定: `getHistoricalProcessExitReasons` で終了理由(OS による kill、ユーザー操作など)を取得し、メッセージに反映する。

**完了確認**:
- [x] 短時間の録音で3つの区分が正しく分かれること。
- [x] 録音中に最近使ったアプリ画面からアプリをスワイプで消す、または `adb shell am force-stop io.github.keiai0.sleeprec` を実行し、再起動後に中断が案内されること。

### Phase 2: 音量の計測と保存
**状態**: 完了(2026-09-19)。ビルド・ユニットテスト(15件)・実機確認まで済み。DB は v2(`loudness_samples` 追加、`MIGRATION_1_2` あり)。録音ループで0.1秒ごとに計算し、1秒ごとに集約、サービスが30秒ごと(と終了時)にまとめて保存する。
**目的**: 録音ストリームからフレームごとの音量を取り、時系列で保存する。
**FR**: FR-4.5(基礎)

- 純粋関数 `Loudness.kt`: 0.1秒フレームから RMS と dBFS を計算する。
- 1秒ごとに(平均 dB, 最大 dB)を集約し、セッションに紐づけて保存する。8時間で約2.9万行なので、Room で問題ない。
- 解析ロジックのユニットテスト(無音、既知の振幅のサイン波)。
- 全録音の WAV の扱いは、§6 の #2 を参照(再検討中)。

**完了確認**:
- [x] 話し声や拍手で dB が上がること(実機で確認: 最小 -62 dB、最大 -8 dB)。
- [x] テストが通ること。

### Phase 3: 音声イベントの検出とクリップ保存
**状態**: 完了(2026-09-19)。実機でイベント検出とクリップ保存を確認済み。閾値(開始 -40 / 終了 -45 dBFS など)は暫定値で、`Thresholds.kt` に集約。デバッグ表示は、デバッグビルドの録音中の画面に出る(現在の dB、閾値、イベント数)。全録音の WAV は、設定画面ができるまで従来どおり残す(§6 #2)。
**目的**: 一定音量を超えた区間を1件のイベントとして切り出す。
**FR**: FR-4.5, 4.7(検出と保存まで)

- 状態機械 `EventDetector.kt`: 閾値超えで開始、一定時間下回ったら終了(ヒステリシスあり)。開始の前 2〜3 秒を含めるため、リングバッファを持つ。
- イベントを `AudioEvent`(開始時刻、長さ、最大/平均 dB、クリップのパス、種別=未分類)として保存する。
- クリップは 16kHz/16bit の WAV として `clips/` に保存する。
- **保持ポリシー**(決定 #6): 1晩(1セッション)あたり最大 **20 クリップ**まで音声を保存する。20 を超えるイベントは、**メタデータ(時刻、長さ、最大/平均 dB、種別)だけ**を記録し、音声は保存しない。保存するクリップは、最大 dB の大きい順に選ぶ(暫定)。
- **自動削除**: 音声(クリップ、および全録音をオンにした場合の WAV)は、**7 日**で自動削除する。アプリの起動時と、セッションの終了時に、期限を過ぎたものを削除する。スコア、指標、イベントのメタデータは削除しない。
- 閾値は暫定値。**閾値調整用のデバッグ画面**(現在の dB とイベント数を表示)を作る。

**完了確認**:
- [x] 部屋で咳や物音を立てると、イベントが検出されてクリップが残ること。無音の夜に大量のイベントが出ないこと。

### Phase 3.5: クリップの再生
**状態**: 完了(2026-09-19)。実機で確認済み。記録(セッション)単位の削除は、この範囲に含めず Phase 8 で行う(決定)。画面遷移は、画面が少ないので自前の状態で行っている(Navigation Compose は Phase 6 で導入)。ホーム画面の「記録一覧」から開く(録音中は非表示)。再生音の補正は `LoudnessEnhancer`(最大 +12 dB)。
**目的**: 検出したイベントのクリップを、スマホ上で聴けるようにする。市場の参考アプリ(すりーぷまいすたー、SnoreLab)では、「毎朝録音を聞く」「グラフをタップして聞く」が使い方の中心([UX.md](UX.md) §6-2b)。Phase 7 まで待たず、クリップができたらすぐ実装する。
**FR**: FR-4.7, 4.8(再生の部分)

- セッション一覧: 開始日時、長さ、状態(通常 / Short Sleep / 中断)、イベント数。新しい順。これが Journal(FR-5.1)の原型になる。
- セッションを開くと、イベントのクリップ一覧(時刻、長さ、最大 dB)と、音量グラフ(Phase 2 のデータ)を表示する。グラフのタップで、最も近いクリップを再生する。
- 再生: 再生・一時停止、シークバー。再生には `MediaPlayer` を使う。
- 音量が小さい端末に備えて、再生時の音量を補正する(SnoreLab のレビューに、再生音が小さいという不満があった)。
- 削除(クリップの WAV と行の両方)。
- 7 日を過ぎて音声が削除されたイベントは、一覧に残し、「音声は削除済み」と表示する(再生ボタンは出さない)。
- 波形の表示、再分類、ダウンロード、共有は、Phase 7 で追加する。

**完了確認**:
- [x] 録音したセッションが一覧に出て、クリップの再生・シーク・削除ができること。

### Phase 4: 音の分類(いびき・寝言など)
**目的**: イベントを種別に分類し、いびき・無呼吸の指標を出す。
**FR**: FR-4.5, 4.6, 4.7

- 方式の第一候補は、学習済みの音響分類モデル(YAMNet の TFLite 版など)を端末上で使う方法。入力が 16kHz/モノラルで、現在の録音形式と一致する。**導入前に、ライセンスと対応クラス(いびき、咳、話し声など)を調べて確定する。**
- 分類対象は SPEC の種別(いびき/寝言/咳/歯ぎしり/おなら/足音/動物/環境音)。モデルが対応しない種別は「その他」にまとめる。
- いびき集計: 頻度、最大/平均 dB、合計時間、発生時刻。
- 無呼吸(目安): いびきが続いたあとに一定秒数以上の無音区間があるものを候補にする。**無音区間の前後を含めてクリップを保存する**(市場のレビューで要望が多かった点。[UX.md](UX.md) §6)。頻度、重症度レベル、最大/合計継続時間を記録し、しきい値超えでリスクを表示する。
- 誤分類に備えて、再分類(FR-4.8)のデータ構造を先に用意する。

**完了確認**:
- [ ] いびき音の動画を再生して録音し、いびきとして検出されること。分類の一致度は、正解を自分で付けた数十件で確認する。

### Phase 5: 睡眠推定と指標
**目的**: セッションから睡眠曲線・指標・スコアを算出する。
**FR**: FR-4.1〜4.4

- 覚醒の推定: 音イベントと(採用する場合)加速度センサーによる体動から、1分ごとに覚醒/睡眠を判定する。
- ステージ: 上記の入力から、Awake/Light/Deep/REM を**暫定ルール**で割り当てる(精度の限界を画面に明記)。
- 指標: 睡眠時間、入眠潜時、Time in bed、各ステージ長と割合、覚醒回数、睡眠負債、就寝/起床のばらつき。
- スコア: Duration / Restoration / Consistency / Feeling の4要素。**計算式は SPEC で未定なので、暫定式を決めて承認をもらう。** 4時間未満などスコアを出さない条件と、その理由ページも作る(FR-4.4)。
- すべて純粋関数で、ユニットテストを付ける。

**決定事項**: 加速度センサーの併用。スマホをベッドの上に置く前提(FR-2.4)なので有効だが、電力と権限(通常は不要)を確認してから決める。

**完了確認**:
- [ ] 既存のセッションデータで、曲線・指標・スコアが再現性を持って算出されること。

- **A**: アラーム(FR-3、`SCHEDULE_EXACT_ALARM`、バックアップアラーム、`RECEIVE_BOOT_COMPLETED`)。
- **B**: スリープサウンドと連動(FR-6 の基礎、FR-2.6、`mediaPlayback` のサービス種別)。
- **C**: Health Connect、Fitbit 連携(FR-7)。
- **D**: 睡眠動物、多言語、バックアップなど。

## 5. 進め方
- 各フェーズの着手前に、その内容を確認してもらいます。完了後は「完了確認」の項目で動作を確認してから、次へ進みます。
- 長時間テストは行わない方針なので、検証は次の3つで行います。
  1. 解析ロジックのユニットテスト。
  2. 既存 WAV の流し込み。
  3. 短時間の実機テスト。
- Phase 1 を先にする理由は、中断検知と保存の仕組みが、以降のすべてのデータの土台になるためです。
